# EDGE<span class="y">fab</span> build plan

**Status: proposed, 2026-10-25; extended 2026-10-26** (Blender assets beside Unreal's, animation as a key focus). **The first build agreed with the owner on 2026-10-30** ([below](#the-first-build-agreed-2026-10-30)): F1 is a textured GLB, imported or generated by Tripo, added to the project and placed with EDGEbuilder, with collision and LODs. Written from the owner's vision (below), on top of [design draft 0.1](design.html). Nothing is built. F0 agrees this plan with the owner. Until then every other phase, name and order here is a proposal. Anything not yet checked is marked unverified.

## The vision

The owner, 2026-10-25:

> EDGEfab is not a mesh editor the way Blender is. It is a **full-spectrum fabricator**: it can load a mesh and do things with it, but its goal is the **game asset**. So clothing, props, characters, NPCs and everything that goes with them. It connects to MCP servers like Blender's and Unreal's for meshwork, and to AI services like Tripo for text to mesh; the ultimate goal is to prompt new assets. `.mesh` files still open REDcode's 3D viewer when clicked, and the right-click menu adds **Open in EDGEfab**, where an asset is changed in one place, by prompts.

| The unit of work | What it includes | |
|---|---|---|
| A **prop** | Mesh, materials and looks, entity, collision, LODs; placed in a scene by EDGEbuilder | First |
| A piece of **clothing** | A mesh per body, looks, item record, name, icon, layering | |
| A **character or NPC** | Body, head, hair, clothes (its appearances), rig and animations, voice, its records (who it is, how it behaves), where it stands | The big one |

Blender, Unreal, Tripo and EDGEmat are tools EDGEfab orchestrates. EDGEfab itself owns the asset: what it is made of, that its files agree, and getting it into the game.

| The modder says | EDGEfab sends it to | What comes back |
|---|---|---|
| "Make the jacket green and the sleeves red" | **EDGEmat** (colors, `mat_apply`), on the parts named "jacket" and "sleeves" | A new look on the same garment |
| "Make an old worn trenchcoat" | **Tripo** (text to 3D), then EDGEfab's Blender steps (clean, fit to V's bodies, weights), then **EDGEmat** (a worn material) | A new garment V can wear |
| "Animate the pinwheel" | **Blender** or **Unreal Engine** (a looping clip on a small rig) | An animated prop |
| "Give this NPC a deeper voice and a leather coat" | **EDGEwave** for the voice, EDGEfab's clothing for the coat | The same NPC, changed |
| "Bring in this Fab prop" | **Unreal Engine** (export, bake), then Blender, then REDbridge | A placeable prop ([UE5 assets](ue-assets.html)) |

The long-term goals: bring free and royalty-free Unreal Engine and Blender assets into the game, and prompt new assets from nothing.

The owner, 2026-10-26:

> Import the same kinds of assets from Blender as from Unreal: meshes, materials, rigs, animations, the things the RED engine naturally accepts. Exotic assets unique to Blender or Unreal and not native to the RED engine are left aside for now. The Cyberpunk modding community strongly wants easy tooling for importing or generating animations, so animation is a key focus. An animation is almost always attached to something, so the something usually comes first, and the modder sees what the thing is.

## What changes in the design

Draft 0.1 said "EDGEfab does not connect to Blender: the assistant connects to both servers". The vision changes that. **EDGEfab becomes the place where the modder works on an asset by prompts**, so it needs its own agent that connects to the other servers as their client. Its MCP server stays, so Claude Code and REDagent can still drive everything from outside.

```
                         ┌──────────────────────────── EDGEfab (VS Code) ─────────────────────────────┐
 Open in EDGEfab on a ──►│  The asset: 3D view (body, clothes, animation) · parts · looks · voice ·   │
 .mesh, .ent, .app or    │  records · files that make it · checks · history · prompt bar              │
 a Character/Item record │                          │                                                 │
                         │                       the agent  (Claude Agent SDK, the modder's own key)  │
                         └──┬─────────┬─────────┬─────────┬─────────┬─────────┬─────────┬────────────┘
                         EDGEmat   EDGEwave   REDcode    Tripo    Blender   Unreal    REDnode, EDGEbuilder
                        materials   voice   files, pack text→mesh (opt-in) (opt-in)  try it, place it
                            │                   │                    │        │
                            └──── REDbridge (game files) ────────────┴────────┴── EDGEfab's own background
                                                                                   scripts (blender --background,
                                                                                   UnrealEditor-Cmd)
 EDGEfab's own MCP server ◄── Claude Code, REDagent (the same tools, from outside)
```

| Decision for F0 | Recommendation | Why |
|---|---|---|
| What EDGEfab opens | **A game asset**, reached from any of its files: a `.mesh`, `.ent` or `.app`, or a TweakDB `Character` or `Items` record. EDGEfab finds the rest of the asset from there | The asset is the unit, not the file |
| The agent inside EDGEfab | **Claude Agent SDK, with the modder's own Anthropic API key**, as REDagent decided | Anthropic doesn't allow claude.ai login in third-party products. The SDK connects to MCP servers over stdio and HTTP. Whether it packages cleanly inside a VS Code extension is unverified |
| Without a key | Everything still works by hand (buttons and fields), and Claude Code can drive it through EDGEfab's MCP server | AI stays optional, as in every EDGE tool |
| Two layers for Blender, and the same for Unreal | **Fixed steps run by EDGEfab's own scripts** in the background (`blender --background`, `UnrealEditor-Cmd -run=pythonscript`). Free-form work goes through the opt-in Blender MCP or Unreal MCP servers | The fixed steps are safe and give the same result every time. Free-form steps are where an AI writes code, so the modder opts in |
| Tripo | **EDGEfab's own client for Tripo's REST API** (v3), with the modder's own key from the EDGE tools' shared key store (`%APPDATA%\Edgemodders\keys`, REDnode's `keys.mjs`), the same way EDGEmat calls its image services | Tripo has no official MCP server (community ones exist). The REST API covers text and image to 3D, decimation, texturing and rigging. One client is easier to guard than a third-party server |
| Other text-to-mesh services | Later, behind the same interface (Meshy, Hunyuan3D, Rodin) | One service first |
| Open in EDGEfab beside Open in EDGEmat | Both stay: EDGEmat for editing a material by hand, EDGEfab for the whole asset, which calls EDGEmat | To confirm with the owner |
| Where animation sits | **Split F7**: animated props (F7a) right after F2, character animation (F7b) right after F5, ahead of F6. **Split again 2026-11-04** (owner): F5a and F7b-1 move up after F7a; see "Rigs and animation: where they live" | Animation is a key focus, and each half needs only its subject in the view: a prop (F1, F2) or a whole character (F5). See "Animation: a key focus" |

### Words to parts

"The sleeves" must name something EDGEfab can change. On a game asset a part is a **submesh**, a **mask layer** in a multilayered material (EDGEmat already maps layers), or, on a character, an **appearance part** (head, torso, legs, a garment). EDGEfab keeps a **part map** per asset: plain names for those parts. The map is made once by rendering each part highlighted, asking the model to name it, and letting the modder correct the names. It is stored with the project. The agent then resolves "sleeves" through the map, never by guessing. If no part matches, it asks.

### Licenses travel with the asset

Every asset EDGEfab brings in records where it came from and under what terms: a Fab listing and its license, a Tripo task and the modder's plan, a UE project of the modder's own. The record goes into the project's manifest and into a credits file in the packed mod. **Tripo's terms** ([Terms of User Agreement](https://www.tripo3d.ai/terms), last updated July 11, 2025, read 2026-11-01):

| | Free users (5.2.1) | Paid users (5.2.2) |
|---|---|---|
| Who owns the model | **Tripo keeps all rights**, the IP included | **The modder** has all rights: use, change, distribute, license, sell |
| Tripo's use | Anything | A licence to use and show it as needed to run the service; **not used to train** its AI |
| In a released mod | No: the rights are Tripo's | Yes |

Some third-party summaries and one Tripo blog say free models are CC BY 4.0. The terms themselves don't say that, so EDGEfab goes by the terms. A modder's inputs are their own responsibility (section 3.1): words and images must not infringe anyone's rights, which matters when an image of a game asset is sent (Wardrobe Designer's Reshape, EDGEfab #3). The owner is on **Pro**, a paid plan. No separate terms for the API were found (platform.tripo3d.ai is a script-only page; the terms say supplemental terms would be shown at sign-up). So EDGEfab asks the modder once, in Tripo's setup, whether their plan is paid or free. It records that in each asset's `license`, and warns on a free plan that the model is Tripo's and cannot go in a released mod. It shows the terms; it never decides for the modder.

### Blender and Unreal, the same kinds of asset

EDGEfab imports the same kinds of asset from Blender as from Unreal: **what the RED engine accepts natively**. Blender is the easier source, since Cyberpunk modders already use it with WolvenKit's Blender add-on and it runs headless with no project. Unreal needs its export step first ([UE5 assets](ue-assets.html)).

| Kind | From Blender | From Unreal | In the game |
|---|---|---|---|
| Static mesh with textures | A `.blend`, or GLB/FBX it exported | A Static Mesh, exported by EDGEfab's script | `.mesh` over a template, `.xbm` textures |
| Materials | Principled BSDF: base color, normal, roughness, metallic | Material inputs, or baked (UE5 assets, U2) | The game's material templates (through EDGEmat) |
| Skinned mesh on the game's rig | An armature with the game's bone names | A Skeletal Mesh moved onto the game's rig | `.mesh` with skinning, `.rig` |
| A small rig of its own (a prop that moves) | An armature | A skeleton | `.rig` and `.anims` on an entity |
| Animation | Actions | Animation Sequences, retargeted in Unreal | `.anims`, played by the entity or a workspot |
| Shape keys / morph targets | Shape keys | Morph targets | `.morphtarget` (WolvenKit import unverified) |
| LODs, collision | Lower-detail copies; simple shapes | LODs; simple collision | Mesh LODs; the entity's physics |

**Left aside for now** (not native to the RED engine): Blender's geometry nodes, particles and hair systems, simulations, drivers and constraints, procedural shaders; Unreal's Blueprints, Niagara, Control Rig, Chaos, Groom, Substrate's layered materials and MetaHuman's facial rig logic. EDGEfab says so plainly when a source holds them, and bakes what it can (a procedural shader into textures, a simulation into an animation, a constraint into keys) only where the result is a plain asset.

Blender sources arrive with each asset kind: `.blend` and FBX props in F3 (right after F1, which takes GLB only), clothing in F4, animation in F7. Unreal keeps its own phase (F8) for its export step.

### Animation: a key focus

The modding community wants easy tooling for importing and generating animations, and today it means WolvenKit, Blender and many manual steps. EDGEfab makes it a key focus, built on one rule: **the subject comes first**. An animation is almost always attached to something, so EDGEfab opens the thing (a prop, an NPC, V's body) and shows it in the 3D view before any animation work starts. Then:

| Step | What the modder does | What EDGEfab does |
|---|---|---|
| See the subject | Open in EDGEfab on the prop or NPC | Shows it on its rig, with the animations it already has, playable |
| Bring in | Drop a Blender `.blend` action, an FBX or GLB clip, an Unreal sequence (F8) | Checks the bones against the subject's rig, retargets what it can (in Blender's or Unreal's background), says what it cannot |
| Generate (later) | "Make him lean on the wall and check his phone" | A text-to-motion service behind the same interface as Tripo; candidates unverified, chosen when the phase starts |
| Preview | Scrub and loop it on the subject | Plays it in the 3D view |
| Use it | "Play it when he stands here", "loop it", "add it to his idles" | Writes the `.anims`, the entity or workspot, the records; Try it in the running game |

### Rigs and animation: where they live (owner, 2026-11-04)

Asked by the owner after EDGEquest's Trauma Team experiments (2026-11-03): reusing a game animation can need a small change to it, so the modder needs to find the game's animations, see them on the character or object that plays them, change them, and see the result there, without hopping between tools. Agreed with the owner on 2026-11-04:

| Decision | Why |
|---|---|
| **Rigs and animation live in EDGEfab**, as a module with its own editor tab (the animation tab), not a separate extension | An animation is judged on its subject, and the assembled character (F5a) is EDGEfab's; a separate tool would rebuild it or fetch it across extensions, which is the hopping to avoid. Skin weights (F4) and prop rigs (F7a) share its core |
| **Built so it can move out**: its own core folder, editor tab and MCP tools (`fab_anim_*`) | If it is wanted without a subject, or its libraries make EDGEfab heavy, it becomes its own extension without a rewrite |
| **EDGEfab owns the animation index**, in its API and MCP server; EDGEquest's Animation picker uses it | One index, not two. It finds an animation by name, by the character or object that uses it (an entity's animation sets), and by the scenes that play it |
| **F5 and F7b split** (F5a and F7b-1 earlier) | Seeing is cheaper than editing, and serves EDGEquest too; the owner's Trauma Team mod gives F7b-1 its test |

**What stays with other tools:**

| Work | Home |
|---|---|
| Game file reads and writes: `.anims` to GLB and back, a whole character to GLB | REDbridge. WolvenKit has `ExportAnim` (an `.anims` with its rig to glTF) and `ImportAnims` (glTF to `.anims`) in `AnimationTools.cs`; `project.export` already writes an `.anims` with its rig as a GLB (checked 2026-11-04); import is not offered yet ([REDbridge #14](https://github.com/Edgemodders/REDbridge/issues/14)) |
| The 3D view and animation playback | REDcode's viewer, shared, so every tab looks the same ([REDcode #21](https://github.com/Edgemodders/REDcode/issues/21), filed by EDGEquest: play an animation on its rig, `openAnimation`) |
| Watching it in the running game | REDnode ([REDnode #39](https://github.com/Edgemodders/REDnode/issues/39), filed by EDGEquest: play an animation or a workspot on a spawned character) |
| Scenes: who plays which animation, when and where | EDGEquest: it picks clips, EDGEfab makes and changes them |
| Looks; voice; placing in the world | EDGEmat; EDGEwave; EDGEbuilder |
| Heavy keyframe work | Blender, through its MCP server or its background |

Vehicles and weapons fit the same way later: whole assets with their own rigs and animations (an AV's doors, its landing).

**Moving between tabs.** One subject, many tabs. Clicking an NPC opens EDGEfab's character tab with the character assembled and playing its idle. Its toolbar offers change clothes (F4), change the look (EDGEmat on that part), open an animation in the animation tab, Edit in Blender, and Try it in the game (REDnode). Every tab works on the same Desk item, so a change anywhere (a clip edited, a recolor, a Blender round trip) redraws the character in the others. A breadcrumb row leads back, as EDGEquest's step view has.

**What editing an animation means:**

| Level | Examples | Where |
|---|---|---|
| 1. Timing | Trim, loop, speed, mirror, blend two clips | The animation tab (F7b-1) |
| 2. Offsets | Move or scale the root's motion; a layer that turns one bone over the clip | The animation tab (F7b-1) |
| 3. Keyframes | A pose, bone by bone | Simple changes in the tab; real work in Blender (F7b-2) |
| 4. New motion | Text to motion through an AI service, retargeted onto the game's rig | F7b-2, with the agent in FA |
| 5. From elsewhere | Unreal and Mixamo clips, retargeted | F8 |

**The test case: Trauma Team's crew** (EDGEquest's experiment X2, 2026-11-03). A Trauma Team crew dropped from MaxTac's AV jumps a fixed height: with the AV lowered to 2 m, they fell through the ground. The drop is in the crew's exit animation, so scaling the root's fall to the new height is a level 2 edit. **Unverified:** which file holds the exit animation. Changing the game's file would change MaxTac's crews too, so the edited clip likely needs to be a new animation used by the owner's AV only; whether that works is open.

## The first build, agreed 2026-10-30

The owner's round trip: **import or generate a fully textured mesh, convert it to something the game can use, Add to Project (the open REDcode project), then place it in the game with EDGEbuilder.** Small, but it touches every tool once, and every later asset reuses its path.

| Step | How | Built on | Unverified |
|---|---|---|---|
| 1a. Import | A textured GLB from disk | | |
| 1b. Generate | Words (or an image) to **Tripo**, with the modder's own key from the EDGE tools' shared key store. Its source and terms go in the asset's record. Ask for a `face_limit` (about 20,000) | Tripo's **v3** REST API (`openapi.tripo3d.ai`; v2 shut down 2026-10-31) | Checked 2026-10-31 ([Tests](testing.html#f0-check-tripo-text-to-model)): a GLB in about 2 minutes for 20 credits; one mesh; 1.4 million triangles without a limit, 19,021 with `face_limit` 20000; Color, ORM and NormalGL textures at 2048²; `auto_size` puts real size on the node. Terms read 2026-11-01 (above, "Licenses travel with the asset"): paid plans give the modder all rights, free plans leave them with Tripo |
| 2. Prepare | In Node, no Blender: node transforms baked in, the base put at height 0, **MikkTSpace tangents** (WolvenKit refuses a GLB without them), under 65,535 **vertices** per submesh, one primitive per mesh, **LODs** made by simplifying and named `submesh_00_LOD_1`, `_LOD_2`, `_LOD_4`, textures taken out | glTF-Transform 4.5.1, mikktspace, meshoptimizer (all MIT): tried in F0 | Checked 2026-11-01 ([Tests](testing.html#f0-check-a-glb-imported-over-a-game-prop)): REDbridge imports the prepared drum over a game barrel with 3 LODs |
| 3. Convert, **Add to Project** | The mesh imported over a prop template. Materials from the model's own textures, by EDGEmat ([EDGEmat #4](https://github.com/Edgemodders/EDGEmat/issues/4)). An `.ent` with the mesh as an `entMeshComponent` and **collision as an `entPhysicalMeshComponent`**, static unless the modder asks for a dynamic prop; its appearance names match the mesh's. Paths lowercase, no spaces, under the mod's own folder (`<modname>\...`). The shape EDGEbuilder asked for in [EDGEfab #2](https://github.com/Edgemodders/EDGEfab/issues/2) | `REDcodeApi.importFile(file, { template })`, REDbridge 0.11.0's texture setups, EDGEmat's API | Checked 2026-11-01 without the game: the import keeps the template's materials and its cooked collision shape, so Add to Project replaces both. Game props are solid through an `entColliderComponent` with a box; an `entPhysicalMeshComponent` takes the mesh's cooked shape, which EDGEfab cannot make. **Open, in the game:** a fitted box in an `entColliderComponent`, or in the mesh's physics data under an `entPhysicalMeshComponent` |
| 4. Pack and install | Pack the project, install it with EDGEdeck | `REDcodeApi.pack()`, `packAndTry()` | Hot load waits for RED Hot Tools on 2.5: start or reload the game |
| 5. Place | EDGEbuilder's Browse shows the prop from the project's loose files or the packed archive; the modder drops the `.ent`, saves the scene, and later bakes it | EDGEbuilder's **B2c, built in EDGEbuilder 0.4.0** (2026-10-30, waits for its test): Browse lists the open project's `source\archive` (through REDcode's `redcode` service, REDcode 0.10.5) and mod archives, and drops a `.mesh` or `.ent` | Its B2c test is to place EDGEfab's first prop |

**What EDGEbuilder's bake probe found** (game 2.5, 2026-10-30, [its tests](https://edgemodders.github.io/EDGEbuilder/testing.html#bake-probe)): a baked `.mesh` becomes a `worldMeshNode`, which only draws, so V walks through it even when the mesh has `meshMeshParamPhysics`. A baked entity with an `entPhysicalMeshComponent` is solid. So the entity is what places a solid prop, until EDGEbuilder's B4 finds a node type that gives a bare mesh collision. Streaming distance is the scene's, so the files need nothing for it.

### The Library (in F1, decided 2026-10-31)

The owner: the Library is a key shared resource for working across the tools, between projects. An asset found in REDcode's game assets goes into the Library, EDGEfab changes it there, and several projects pull it in. Optional, but useful for some workflows. The details, and the asset item proposed for it, are on [Library assets](library.html).

The owner, 2026-11-02: EDGEfab has a **Desk**, as EDGEmat does, and the Desk becomes a norm for the EDGE tools. It is a persistent scratch workspace, where objects in progress are kept and later added to projects or stored in the Library.

| In F1 | |
|---|---|
| EDGEfab's **Desk** (built 2026-11-02, from the Made view) | Where a prop made from a GLB or by Tripo lands: `%LOCALAPPDATA%\EDGEfab\desk\<name>.prop.asset/`, kept between sessions. Each item already has the Library's asset shape (`asset.json`, laid out like a small project, the kind in the name; owner 2026-10-31), so moving it is a copy. MCP `fab_desk` |
| **Add to Library**, from the Desk | Stores a Desk item in the Library, in a folder the modder picks or under its game path (**Use the game path**), when a Library root is set |
| EDGEfab's **Library view** | The modder's own folders (not game paths), with their assets and model files (GLBs kept to convert later); open, Make a prop, Add to Project, Refresh from Library |
| **Add to Project**, from the Desk or the Library | Copies the asset's game files into the project; from the Library, with a note of where they came from |
| Without a Library | The Desk and Add to Project work alone |
| Not in F1 | REDcode's **Add to Library** on game assets ([REDcode #19](https://github.com/Edgemodders/REDcode/issues/19)), changing an asset that came from the game (F2, with Open in EDGEfab) |

## Reshape, built in EDGEmat first (read 2026-11-03)

EDGEmat built **Reshape** for its REDnode app Wardrobe Designer: a garment V wears, changed by words. The owner's decision (2026-11-02, [EDGEfab #3](https://github.com/Edgemodders/EDGEfab/issues/3)): it is built in EDGEmat's core for now and moves into EDGEfab at a later increment. Source: EDGEmat's design ("Reshape: a garment's shape changed by words"), `extensions/edgemat/src/core/reshape.ts`, `glb.ts`, `tripo.ts`, and its test "Reshape check" (passed in the game 2026-11-02 on a cowboy hat).

| Step | How EDGEmat does it | Checked |
|---|---|---|
| 1. Views | The game mesh exported through REDbridge and drawn front, left, back and right in its look's colors, orthographic, the garment half of each square so a change has room | 2026-11-02 |
| 2. Change by words | The four views sent **as one picture, two by two**, to an image service with the words, then cut apart: they change together and stay consistent. Refined round by round, with Back. OpenAI's GPT Image 2.5 by default (Gemini drew worse: kept the old brim, changed one side). A few tens of US cents a round. **The pictures decide the result**: Tripo and the fit follow them, mistakes included | 2026-11-02 |
| 3. Model | Tripo's **multiview to model** (`/v3/generation/multiview-to-model`, the four views): about 2.5 minutes and 30 credits, 1.5 million triangles. Then Tripo's **retopology** (`/v3/mesh/decimate`, `bake: true`) to a game's face count with the texture baked on: about 2 minutes and 30 credits | 2026-11-02 |
| 4. | REDnode | `world.spawn` and `world.load` of a project's prop or NPC after a hot load (H2c), equip on V | F2, F6 |
| EDGEbuilder | Its B3c: the `npc` scene kind | F6 |

## How it is built and released

The same conventions as EDGEmat, so the family stays one pattern: a changelog ([Changelog](changelog.html)), every test in [Tests](testing.html), the release gate, releases started only when the owner asks, and the release workflow with Marketplace, Open VSX, npm and Nexus (copied from EDGEmat's in F1; the Nexus box once the page exists). Details in [Dev setup](dev-setup.html) once the code exists.
